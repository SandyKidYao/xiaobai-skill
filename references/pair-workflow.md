# 模式 D:结对开发——完整工作流

这个模式让你(主 Agent)与一个搭档 Agent 协作完成编码任务:编码前对齐方案,编码后交叉 review,review 结论先核实再修复,僵持不下时升级给用户裁决。

核心价值不在"多一双眼睛",而在**独立性**:搭档没有你的实现过程记忆,不会继承你的盲点;而你对搭档的每条意见先核实再动手,防止 reviewer 的"貌似有理但错误"的结论污染代码。整个流程是两层防错:搭档防你的错,核实防搭档的错。

## 状态与产物目录

开工时在**工程根目录**下建工作目录 `.pair-review/<slug>/`,并在创建 `.pair-review/` 时写入一个只有一行 `*` 的 `.gitignore`——整个目录(连同 gitignore 自己)就被排除在版本控制之外,不会误提交。放在工程内有两个实际好处:跑在"限定项目目录的只读沙箱"里的外部 CLI 搭档能直接读到这些文件;用户想翻记录时也不用去临时目录里找。项目不可写或用户明确反对时,退回会话临时目录(scratchpad)。目录里存放:

- `plan.md` —— 对齐后的实现方案。开头记元信息(搭档是谁、session id、项目路径);文末记方案期未采纳的意见(一行理由)和编码期的偏离附记
- `issues.json` —— 问题台账(见 review 循环一节),由主 Agent 维护,是**唯一的跨轮记录**:ID、计数、状态、每轮一行摘要;争议问题(attempts ≥ 2 或将进升级报告)额外记双方立场的短原话引用
- 升级报告 HTML(如触发上报)

有意不做全程逐字记录:流水账没有人会读,维护它违背本 SKILL 降低负担的初衷。用户要过程细节时,你亲历了全程,在 QA 里回答;真正需要可回溯的正式评论记录时,建议走代码托管平台的真实 PR/MR 评论,而不是本地模拟一份。

创建目录后核实一次 `git status`:确认 `.pair-review/` 没有出现在待提交列表里(gitignore 生效),工作文件永远不进用户的版本历史。

## 阶段 0:选择搭档

按优先级选择搭档 Agent:

1. **外部 CLI Agent**(优先):检测系统里是否装有其他 AI 编码 CLI(如 `codex`、`gemini`)。异构模型的视角差异是交叉 review 价值的主要来源。
2. **子代理**(兜底):没有可用外部 CLI 时,用宿主自带的子代理机制扮演搭档。

选定后做两件事再进入阶段 1:

- **建立持久会话**:多数 CLI 支持 resume(如 `codex exec resume`、`claude -p --resume`),让搭档在同一个 session 里走完全程,自然保持上下文;session id 记进 `plan.md` 开头的元信息。
- **发协议简报**:首轮消息附上 [pair-partner-briefing.md](pair-partner-briefing.md) 的绝对路径让搭档先读——它不知道这套工作流,简报让双方信息对称(角色、finding 格式、APPROVE 约定、"讲证据、不空转"规则),后续轮次就只需发增量。

检测方法、会话保持细节、提示词模板、失败兜底,读 [pair-partner-setup.md](pair-partner-setup.md)。选定后用一句话告知用户本次搭档是谁,然后继续,不用等确认。

## 阶段 1:方案对齐

编码之前先和搭档对齐怎么做。这一步的目的是把分歧消灭在写代码之前——方案层面改一句话的事,到了代码层面就是返工一轮。

1. 自己先调查代码库,写出实现方案草稿(目标、改动范围、关键设计决策、测试策略),存入 `plan.md`。
2. 把方案连同必要上下文发给搭档,请它指出:风险点、遗漏的边界情况、更优的替代设计。
3. 处理反馈:采纳的直接改进方案;不采纳的在 `plan.md` 文末记一行"未采纳:意见 X,理由 Y",并回复搭档。
4. 对齐讨论**最多 2 轮**。2 轮后仍有实质分歧的,选你认为更优的方案继续,把分歧记入 `plan.md`——它可能在 review 阶段重新出现,到时按 review 循环的规则处理。

方案本身很小(如几行的 bug fix)时,这一阶段可以压缩成一轮:"我打算这样修,有异议吗"。

## 阶段 2:编码

按对齐后的方案由你实现。正常写代码:小步提交思路、跑通已有测试、为新行为补测试。实现中发现方案有误需要偏离时,偏离点附记在 `plan.md` 文末,重大偏离(改变了对齐过的设计决策)应先知会搭档再继续。

## 阶段 3:review 循环

这是本模式的核心,完整规则(核实方法、台账格式、计数规则)读 [pair-review-verification.md](pair-review-verification.md)。骨架如下:

1. **送审**:把改动(有 git 时让搭档自行 `git diff <基线>` 查看,不落盘生成 diff 文件)、方案、"如何运行测试"发给搭档,要求结构化的 review 结论(每条 finding 含:位置、问题描述、严重程度、建议)。
2. **核实**:对每条 finding,先核实再动手——读代码验证逻辑、跑测试、构造复现。核实结果三选一:
   - **确认属实** → 修复,补上防回归的测试。
   - **无法复现/不成立** → 不修改代码,把你的证据(测试输出、代码路径分析)回复给搭档。
   - **属实但不同意修法** → 修,但按你认为正确的方式,并向搭档说明理由。
3. **记账**:每条 finding 进 `issues.json` 台账,有稳定 ID 和尝试计数。搭档在后续轮次重提同一问题(哪怕换了措辞)时,归到同一 ID 并计数 +1——这是"3 次上限"能成立的前提。
4. **再送审**:修复完成后回到第 1 步,附上每条 finding 的处理结果。循环直到搭档明确表示通过(approve)。
5. **升级条件**:任一 issue 的尝试计数达到 3(即同一问题被提出、你处理、对方仍不认可,往复 3 轮)→ 停止循环,进入阶段 4。整体循环轮数达到 5 轮也强制升级,防止无上限烧钱。

为什么先核实:reviewer 和所有 LLM 一样会产生"貌似有理但错误"的结论。不核实就照改,轻则浪费一轮,重则把对的代码改错。核实的产出(测试输出、复现步骤)同时就是回复搭档的证据和升级报告的素材,一举三得。

## 阶段 4:升级上报

同一问题 3 轮未解决,说明这不是"再试一次"能解决的:要么双方对需求/事实的认知有分歧,要么问题需要的信息(业务意图、取舍偏好)只有用户有。此时把裁决权交给用户。

上报的呈现复用本 SKILL 的既有范式:HTML 报告承载全貌(遵循「汇报与展示」和图示规范),聊天里用模式 B 的 QA 节奏引导。报告结构、模板要求,读 [pair-escalation-report.md](pair-escalation-report.md)。要点:

- 生成一个自包含 HTML 报告:问题时间线、双方立场与证据、三次尝试各自做了什么/为什么没解决、需要用户裁决的具体选项。
- 聊天里结论先行(2~4 句说清卡在哪、需要用户决定什么),附上报告路径,再列 2~3 个推荐问题引导用户理解——不要在聊天里贴长文。
- 拿到用户指导后,带着新信息回到 review 循环,该问题的计数清零重新开始。

## 完成收尾

搭档 approve 后,按模式 B 向用户汇报:做了什么、review 经过几轮、修了哪些问题、哪些 finding 被核实为不成立(附一句证据),再列推荐问题供追问。`plan.md` 和 `issues.json` 保留在工作目录里供查阅;用户想了解过程细节时,你亲历了全程,在 QA 里直接回答,不要让用户去读文件。

## 成本意识

这个工作流的 token 消耗是单 Agent 的 2~3 倍,价值在重要改动上才能兑现。用户只是要一个小改动却触发了本模式时,主动说明并建议:方案对齐压缩为一轮、review 一轮通过即收——流程可以按比例缩放,不必每次全量执行。

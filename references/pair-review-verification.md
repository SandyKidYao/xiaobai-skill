# review 循环:核实方法、问题台账与计数规则

## 核实方法

对搭档的每条 finding,先核实再动手。核实的深度和 finding 的性质匹配:

| finding 类型 | 核实方法 |
|---|---|
| 逻辑错误("X 情况下会出错") | 构造 X 情况的最小复现:写一个失败的测试,或用脚本/REPL 触发。能复现 → 属实;精确按描述构造却不能复现 → 记录尝试过程,判不成立 |
| 边界情况遗漏 | 沿代码路径人工推演该输入的走向,再用测试验证推演结论 |
| 并发/时序问题 | 通常难以直接复现,改为代码路径分析:找出共享状态和交错点,能写出具体交错序列 → 属实;写不出 → 请搭档给出序列 |
| 风格/可维护性建议 | 不需要"复现",判断标准是与代码库现有约定的一致性。符合约定 → 采纳;搭档的偏好与代码库约定冲突 → 不采纳,理由是一致性 |
| 性能问题 | 有量级差异的(如 O(n²) vs O(n))看代码即可确认;无量级差异的要求测量,不凭感觉修 |

核实的所有产出(测试代码、输出、推演过程)保留下来:它同时是回复搭档的证据、升级报告的素材。

**诚实红线**:核实结果如实记录。不能因为想让流程快点结束就把"没复现出来"写成"确认不成立"——没复现出来但推演上说得通的,标记为"存疑",主动请搭档提供复现步骤。

## 修复规则

- 确认属实的 finding:先写一个暴露该问题的测试(红),再修复(绿)。这保证"修复"修的是核实出的那个问题,而不是别的什么。
- 一次只修一个 finding,修完跑全量测试再修下一个,避免修复互相干扰后无法归因。
- 修复引发的新改动也属于下一轮送审范围。

## 问题台账 issues.json

台账是升级机制的地基:"同一问题反复 3 次"要能成立,前提是"同一问题"可以被稳定追踪。它是**唯一的跨轮记录**——不做全程逐字流水账(没人会读,维护是负担)。`history` 里每轮一行摘要;**当某个 issue 的 attempts 升到 2(进入僵持预警区)或将进入升级报告时,该条 history 须补记双方立场的短原话引用**(从搭档 stdout 摘录)——升级报告的"双方立场对比"只有原话才有说服力,而只有争议才值得留原话。格式:

```json
{
  "issues": [
    {
      "id": "ISS-1",
      "title": "并发写入时缓存可能返回过期值",
      "location": "src/cache.py:87",
      "severity": "major",
      "attempts": 2,
      "status": "contested",
      "history": [
        {"round": 1, "partner_said": "get/set 之间无锁,存在竞态", "we_did": "核实属实,加锁修复", "outcome": "搭档复审:锁粒度过大,引入新的性能问题"},
        {"round": 2, "partner_said": "建议改用读写锁", "we_did": "改为读写锁", "outcome": "搭档复审:写饥饿风险,仍不通过"}
      ]
    }
  ]
}
```

status 取值:`open`(待处理)、`fixed-pending-review`(已修待复审)、`resolved`(搭档认可)、`rejected-with-evidence`(核实不成立,搭档已接受)、`contested`(双方仍有分歧)。

字段名严格按上面的模板来(`id`/`title`/`location`/`severity`/`attempts`/`status`/`history`),不要自创字段或改名——升级报告和收尾汇报都按这个 schema 读台账,字段一变它们就读不出历史。没有 finding 时台账就是空的 `issues` 数组,不用造条目。

## 同一问题的归并与计数

- 搭档在新一轮重提某问题时,先对照台账:**位置相同或相邻、指向同一行为缺陷的,归为同一 ID**,哪怕措辞完全不同(如"有竞态" vs "建议加锁")。判断标准是"修好其中一个,另一个是否随之消失"——是,就是同一个问题。
- 归并后 `attempts` +1。**attempts 的语义是"我方处理后对方仍不认可的往复次数"**,不是被提及次数:第一次提出并处理算 1,处理后对方不认可、再处理算 2,以此类推。
- 搭档对同一位置提出了性质不同的新问题(如上一轮说竞态,这一轮说内存泄漏),开新 ID,不算重提。
- `attempts` 达到 3 → 该 issue 触发升级,停止循环,进入升级上报。
- 整体循环轮数达到 5(无论单个 issue 计数)也触发升级,理由写"循环未收敛"。

为什么是 3:一次往复可能是表达不清,两次可能是修法不对,三次仍不收敛,大概率是双方对"什么是正确行为"有认知分歧——这类分歧再循环十次也不会自己解决,需要的信息(业务意图、取舍偏好)在用户手里。

## 用户裁决后

用户给出指导后,带着新信息回到循环:

- 该 issue 的 `attempts` 清零,`history` 里记一条用户裁决的内容。
- 把用户的裁决转告搭档(写进下一轮送审的上下文),明确"此点已由用户裁决,不再讨论,除非你有新的事实性证据"。
- 同一 issue 在用户裁决后又打满 3 次(极少见),再次升级时报告里要突出"上次裁决为何没解决问题"。

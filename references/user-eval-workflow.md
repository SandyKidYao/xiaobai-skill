# 模式 E:用户视角验证——完整工作流

这个模式给已完成的交付物接入它本来缺少的**外部用户视角**:派出若干彼此隔离的虚拟用户,让他们在真实入口上办自己的事,再从行为轨迹里读出反馈。

核心价值在于视角的独立性:你(以及模式 D 的搭档)都是建造者,知道每个功能在哪里、每个约定为什么存在——这些知识恰恰是真实用户没有的。虚拟用户不评审、不打分、不提意见,只带着自己的目的用一次;他理解了什么、在哪里卡住、什么时候放弃,全部从行为里**读出来**,而不是让任何 Agent 写评审意见。

两条设计底线,贯穿全流程:

- **判断从行为里读出,绝不写进去**:人设和场景里不得出现对被测物的评价、预期问题或"留意 X 好不好"式的暗示。写进去的判断会变成自证预言——你会得到你写进去的那个结论,而且看起来像是测出来的。
- **证据从真实入口拿到,绝不冒充**:拿不到真实入口不是失败,冒充拿到了才是。降级做更窄的验证可以,但必须同时改写结论边界,说清这轮验了什么、没验什么。

## 触发与授权

- 用户明确要求(“模拟用户试试”“用用户视角验证一下”“看看好不好用”)时进入。
- 你完成一个重要 feature 或交付物后,认为值得检验时,可以**提议一次**(一句话说明能验什么、大概几个 case、成本量级),用户同意才做,拒绝即作罢。一般性的测试、评审请求不要自动升级成本模式。

进入后先从用户原话确认这次走多深,不擅自升级:

1. **只看反应**:跑一轮,交付反馈,不改目标。
2. **授权修复**:先拿到使用证据,再修改,并用新的虚拟用户复验受影响的路径。
3. **自主循环**:持续改进,直到结果有相称的证据支撑、继续验证不再带来新信息,或剩下必须由用户决定的取舍。

## 状态与产物目录

开工时在工程根目录下建 `.xiaobai/user-eval/<slug>/`。`.xiaobai/` 是本 SKILL 所有模式共用的统一工作目录:首次创建它时写入一个只有一行 `*` 的 `.gitignore`(整个目录连同 gitignore 自己都不进版本控制,创建后用 `git status` 核实生效);已存在时直接在下面建子目录。目录里存放:

- `cases.md` —— 本次验证的元信息:要回答的问题、被验证版本(git commit 或文件指纹)、真实入口、每个 case 的人设与场景定义、可见范围
- `traces/<case>.md` —— 每个 case 的行为轨迹(格式见下)
- `feedback.md` —— 汇总反馈;循环时每轮追加,不覆盖上一轮

项目不可写或用户反对时退回会话临时目录。同模式 D 的理由,不做全程逐字流水账:轨迹本身就是记录,过程细节用户在 QA 里问你答。

## 第一步:判族,定"什么才算真用过"

被测物按"人怎么碰到它"分四族,这决定真实入口、证据形态和最容易翻车的地方:

| 族 | 被测物 | 真实入口 | 证据 |
| --- | --- | --- | --- |
| 界面类 | 网页、应用 | 真浏览器/真设备,全新访客状态 | 每步截图 + 关键文案原样摘录 |
| 对话类 | Agent、模型 | 无历史的新会话 | 完整往返,不只留结论 |
| 工具类 | Skill、CLI、库 | 隔离目录真装真跑,不继承你的环境 | 命令 + 输出 + 退出码,安装到跑通之间的每次失败都留 |
| 成品类 | 文档、图片、报告 | 按最终形态渲染后看真实像素 | 所看画面 + 用户对内容的复述原话 |

判错族的代价是整轮证据不成立,而且看起来像成立的:读源码不算用过网页;读 markdown 源文件不算看过渲染后的成品;给 Agent 一个带上文的会话验的是"第二次用"而不是"第一次用";在你自己配好的环境里跑工具,上手成本就被抹掉了——而上手成本往往正是要验的东西。

宿主工具不支持目标的体验方式(比如没有浏览器能力)时,降级做更窄的验证,并在结论里明确边界:"本轮只验证了内容与流程逻辑,交互体验未经真实点击验证"。

## 第二步:写人与写事

怎么把虚拟用户写"厚"、场景怎么写才不污染结果,读 [user-eval-personas.md](user-eval-personas.md)——动笔前先读它,这是全流程最容易做错的一步。

case 数量由"还有什么不确定"决定,不凑数、不配平正反例。一个窄问题一个 case 就够;典型规模 2~4 个;每个 case 都是子代理真实操作,算力真花,超过 5 个先向用户说明成本。多个 case 之间的差异必须真的会改变行为(不同的背景知识、不同的急迫程度、不同的既有工作流),否则跑出来是同一份轨迹的几个副本。

## 第三步:隔离派发

每个 case 用一个**干净上下文**的子代理(或无历史的新进程),它收到的全部信息是:

- 自己的人设与场景;
- 目标入口与可见范围(界面类给 URL 和"不许读源码";工具类给隔离 cwd 和安装说明;成品类给渲染后的文件);
- 轨迹记录要求(见第四步)。

**不给**:验证问题、其他 case、历史反馈、你的修改意图、对被测物的任何背景解释。它是来办事的,不是来配合验证的。

派发指令附两条真实性约束:

> 你的工具能力不会扩大这个人的知识和权限:只做他现实中会做的动作,用 shell 就记录真实命令,只有实际操作了界面才能写"点击"。做不到他会做的真实动作时,停下并如实说明限制,不要用别的方式代做后宣称成功。
>
> 每步先观察再决定。声称办成之前,对照场景的成功条件在当前观察里逐条核实——核不过就继续或如实放弃,不凭意图和记忆宣告完成。

多 case 之间状态完全隔离(独立目录、独立会话、独立浏览器上下文),没有共享可变状态才并行,否则串行——串行不损失信号。

## 第四步:轨迹与复核

每个 case 产出一份轨迹,逐步记录:

- **想法**:影响这一步的简短理由(以这个人的知识和判断方式);
- **动作**:实际做了什么(字面命令、按可见文字描述的点击、说出的话);
- **观察**:真实结果(输出关键片段、看到的画面、对方的回复),证据文件放 case 目录并引用。

终态四种:**办成**(须有可指认的证据支撑每个成功条件)、**自然放弃**(写出这个人现实中会放弃的理由)、**预算耗尽**、**环境故障**。环境故障是你的问题不是用户行为,修好环境后干净重跑;但目标自身打不开、报错,是用户的真实经历,照实记录,不能当成环境故障抹掉。

主代理收轨迹时复核:动作与实际工具记录一致吗?声称办成的 case 在轨迹里找得到证据吗?不一致的 case 作废重跑,不进反馈。步数预算给个常识值(界面类 8~15 步、对话类 4~10 轮、工具类 10~20 步、成品类 3~6 步)——真人不会在一个页面上试二十次。

## 第五步:读轨迹,出反馈

结合要回答的问题读所有轨迹,分清三层:直接观察到的行为、有证据支持的解释、尚未验证的推断——反馈里逐条标明是哪一层。

**办成的轨迹要按"摩擦"再读一遍**:首步的犹豫、耗在无关区域的步数、说出口的抱怨、自己动手绕过或返工的地方。办成了但办得费劲,是成功轨迹里唯一藏着的结构信号;只按结果读,这层就丢了。反复出现却容易被归成"个人习惯"的行为(每个人都先自己返工一遍才用),是最高优信号而不是噪声。

改进建议写成**需求**而不是实现方案:哪类用户、在什么处境、需要得到什么结果,附证据回指(哪个 case 第几步发生了什么)和不满足的后果。"首次使用者需要不查外部资料就能跑通第一条命令"是需求;"README 加一节配置说明"是实现方案——后者只有在用户已授权修复时才另列一段。优先级按后果和证据强度排,不按出现次数投票:一个关键用户在关键路径上的失败,比多个低影响摩擦更重要。

交付遵循本 SKILL 的既有范式:聊天里按模式 B(结论先行 + 推荐问题),case 多或用户要全貌时生成 HTML 报告承载细节(遵循「汇报与展示」),轨迹与证据文件路径附在报告里。

## 需要循环时(仅限已授权)

1. 修改前记下被验证版本(commit/指纹);修改后用**全新的**子代理复验受影响的路径——不给它上一轮的反馈和修改说明,否则验的是"知道答案的人"。
2. 声明与证据对应:说"这个问题已修复",要有受影响用户的新行为证据;说"整体更好",要有同口径的前后对比;换了人设或场景,如实说这是覆盖范围变化,不能算提升。
3. 每轮显式判一次**该补还是该另起**:受阻点都落在具体元素上,补;不同用户卡在同一个结构层级、改动清单全是"再加一块"、有人每轮都返工同一处,考虑另起。另起版交给没见过现版本的子代理从素材和需求清单从零生成,与补丁版跑同一批 case,赢了才换,平局不换。你给自己的方案判"只需要补丁"天然可信度不足——判之前先自问"假如这不是我做的,只看轨迹我会怎么判"。
4. 停止条件:连续两轮没有新增的高优先级需求、且已修需求都拿到了新行为证据 → 收敛;这批视角的信息枯竭但目标未必够好 → 如实说"在这批视角下已饱和",要么换用途不同的人,要么收口;剩下必须由用户决定的取舍 → 复用模式 D 阶段 4 的升级上报范式(HTML 报告 + 模式 B 引导),请用户裁决。

## 成本意识

每个 case 是一个子代理的完整真实操作,token 和时间都是真花的。用户拿小交付物触发时,主动说明并压缩:1~2 个 case、只看反应不循环。与模式 D 衔接时(重要 feature 走完结对开发再验效果),两个模式的成本叠加,提议时一并说清。

# 模式 E:怎么写虚拟用户与他的事

虚拟用户不是一段角色设定,它是一个要在陌生界面上自己决定下一步的 agent。它凭什么决定?凭它**想起了什么**。所以人设的重心不是身份标签,而是可以被当前处境唤起的具体经历。

写薄的代价不是不精致,是**行为消失**:一个只有"资深工程师,注重效率"这类标签的人设,模型没有任何可调用的具体经验,只能退回先验——一个耐心、积极、什么都愿意再试一次的"平均人"。几个这样的人跑同一件事,会给出几份几乎一样的轨迹:看着像多视角,其实是一个。

## 倒着写:经历 → 本事 → 身份

先定身份再补例子,写出来的三段是同一句话的三种说法,密度是假的。倒过来:

1. **先攒经历**:他这些年具体用过什么(具名工具、哪一年、哪个版本)、干成过什么、被什么坑过、哪次翻了车。每条经历写三样:当时的处境、真做了什么、留下了什么判断——"判断"是这条经历还留在脑子里的原因,也是它影响今天行为的通路。
2. **再抽本事**:从经历里读出他真正的操作流——他反复做对的那几件事是怎么做到的。写机制,不写"遇到 X 就做 Y"的脚本,后者等于替他决定了下一步。
3. **最后蒸身份**:几句话说清他在没经验的地方会怎么取舍、不随环境改变的性情。写到这步会发现很好写,因为它只是在总结你已经知道的人。

经历要具体到什么程度?对照着改:~~熟悉前端工程化~~ → "2019 起用 webpack,2022 主推团队换 Vite,理由是冷启动从 40 秒到 2 秒";~~对新工具持开放态度~~ → "对'AI 帮你写测试'一律先怀疑:抽查过一批生成的测试,断言都在复述实现"。写不出具名工具和年份,说明这个人还没想清。

每人 4~8 条经历、每条两三句话就够;经历的措辞要用**他将会遇到的那类处境的词**(他今天要评估一个 CLI,就写"上次评估一个命令行工具要不要替掉现有流程时……"),这样在对应处境下才会被自然想起。

## 红线:不写对被测物的看法

这条比密度更重要。写"他对**别的**同类东西的既有判断"是人设——解释他为什么形成现在这套标准;写"他会觉得我们这个功能不够直观"是把结论提前塞进轨迹,整轮验证作废,而且看起来像是测出来的。

同理,场景里不写"留意 X 好不好"——那是把用户变成审稿人。人和事只写客观事实与自然处境,所有判断从行为里读出来。

## 同批人要真分叉

把同一个处境摆到几个人面前,取舍应该明显不同。都是"先看文档再动手"就是塌了,回去把经历写开。差异放在哪,按族选最能改变行为的变量:

- **界面类**:他过去用过什么同类产品(决定他先去哪里找功能),手上有多急(决定他试几次就走)。
- **对话类**:他对这类东西的预期(以为一句话能办完,还是准备好来回带它),愿意交出多少上下文。
- **工具类**:第一次碰这类工具还是熟手来评估换不换,他现有工作流里已经有什么(有替代品的人和白手起家的人判断标准完全不同)。
- **成品类**:背景知识水平(术语门槛对不同读者是完全不同的东西),看多久(扫三十秒和读十分钟看到的是两份东西),以及拿到之后用到哪去——**至少安排一个要"转手用"的人**(投屏、发客户、放进自己的材料):只为读懂而来的人不会关心这东西够不够格拿出去,呈现质量只有在"转手"的行为里才会进证据链。

## 场景:一件真事的前因后果

场景是他今天为什么会碰上这件事,三个要素:

- **目的**:想得到什么结果,**以及为什么是现在**。"想试试这个工具"不是目的;"明天要给团队定选型,今天得拿出能跑的证据"才是。
- **处境**:他手上真带了什么材料、有多少时间、已经试过什么、谁在等结果。这决定他愿意折腾几次。
- **收束**:可观察的成功证据,和他会**自然离开**的条件。放弃条件写不出来,这个人就被写成了不会走的人,测不出流失。

不写操作步骤、不写疑似缺陷、不写正确答案。任务必须在实际测试环境里办得成:不要依赖测试环境里不存在的同事、数据或历史记录,否则虚拟用户如实找不到、放弃,而你会把这误读成产品办不成事。

## 派发前自检

- 每个人设有具名、带年份的经历,而不只是身份标签?
- 人和事里搜一遍被测物的名字和"好/不好/直观/易用"类评价词——出现即重写?
- 把同一处境摆给这批人,他们的第一步会不同?
- 每个场景有自然放弃条件?
- 场景里的任务用测试环境里真实存在的东西措辞?

# 搭档接入:检测、会话保持、调用与兜底

## 检测外部 CLI

按下面顺序探测,取第一个可用的(用户明确指定搭档时听用户的):

```bash
command -v codex   # OpenAI Codex CLI
command -v gemini  # Google Gemini CLI
command -v claude  # Claude Code(自己是 Claude Code 时跳过,同源没有交叉价值)
```

其他 AI 编码 CLI(如 `aider`、`opencode`)也可以用,原则相同:支持"非交互式调用、从参数或 stdin 接收提示词、回答写到 stdout"即可。不确定调用格式时先看 `<cli> --help`,不要凭记忆猜参数。

都不可用时,退回子代理方案(见文末)。

## 会话保持:整个结对用同一个 session

多数 AI CLI 支持恢复历史会话。**优先让搭档在同一个 session 里走完全程**——它能自然记住方案讨论、上一轮 findings 和你的反驳,不需要每轮重发全部上下文,对话质量和 token 成本都更好。

已验证的续接方式(以实际 `--help` 为准):

```bash
# Codex CLI:首轮加 --json 从事件流里捕获 session id,后续用 id 续接
codex exec --json "<首轮提示词>"
codex exec resume <SESSION_ID> "<后续轮提示词>"
# 拿不到 id 时才用 resume --last 兜底——注意它续接的是"最近一次"会话,
# 若期间有别的 codex 会话启动会续错对象,plan.md 元信息里要注明用了兜底

# Claude Code:自己生成一个 UUID 作为 session id,全程复用
claude -p --session-id <UUID> "<首轮提示词>"
claude -p --resume <UUID> "<后续轮提示词>"
```

其他 CLI 先查 `--help` 里的 resume/session/continue 能力。注意事项:

- 把 session id 记进 `plan.md` 开头的元信息,断了能续上。
- **会话是优化,文件才是事实来源**:plan.md / issues.json 照常维护。session 一旦丢失或行为异常(搭档明显忘了上文),退回无状态模式——每轮重发简报路径、plan.md、issues.json 和当前 diff,搭档凭这些就能重建工作状态,流程不变。
- 不支持 resume 的 CLI 直接用无状态模式,每次调用自带全部上下文(给文件路径让它自己读)。

## 首次接触:先发协议简报

搭档不知道这套工作流。首轮消息必须让信息对称——把 [pair-partner-briefing.md](pair-partner-briefing.md) 的**绝对路径**发给它,要求先读再干活。简报讲清了它的角色、流程全貌、finding 格式、`APPROVE` 约定和"讲证据、不空转"的规则,这样后续每轮提示词只需要发增量,不用重复协议。

首轮消息模板(方案审阅):

```
你将和我结对编程,担任审阅方。先阅读协议简报,了解流程和你的行为规则:
<pair-partner-briefing.md 绝对路径>
(本 skill 的完整工作流在 <skill 目录绝对路径>,有兴趣可自行阅读)

第一项工作:审阅我的实现方案。
任务背景:<一句话>
方案:<plan.md 绝对路径>
相关代码在当前目录,可自行阅读、可运行测试,但不要修改任何文件。
请按简报中的规则给出意见;没有实质意见就明确说"方案可行"。
```

## 后续轮次(同一 session 内)

会话保持时,后续提示词只发增量:

```
# 送审(编码完成后)
实现完成,请 review。
改动:请在项目目录自行运行 `git diff <基线>` 查看(如 `git diff HEAD`;本轮增量另注明)
运行测试:<命令>
按简报的 finding 格式输出;全部通过则单独输出一行 APPROVE。

# 复审(处理完 findings 后)
上一轮 findings 的处理结果:<逐条:修了什么 / 为什么核实为不成立及证据>
请复审。对不认可的处理结果,给出新的证据或复现步骤,不要只重复原结论。
```

最后一句在每次复审时都要带上——它迫使僵持的分歧向"可验证"的方向收敛,而不是空转措辞。

**diff 的给法:优先用 git,不落盘。**项目有 git 时,直接让搭档在项目目录自己跑 `git diff`,并告知基线(如 `git diff HEAD`)——永远精确、零冗余文件、搭档还能按需局部查看;回合严格串行,搭档 review 期间你不改代码,它看到的就是送审时的状态。只有项目没有 git、或搭档环境确实读不了仓库时,才生成一次性 diff 文件发过去。不要在有 git 的项目里手工维护 diff 文件——它可能忘更新,让搭档审到和工作区脱节的内容。

## 调用注意事项

- 在用户项目目录下调用,让搭档能直接读代码;工作目录 `.pair-review/` 就在工程内,只读沙箱的搭档也能直接读到 plan.md 和 issues.json,不需要额外授权路径。
- 设置超时(如 5~10 分钟)。超时或报错重试一次;连续两次失败,降级到子代理方案并告知用户。
- 每轮结束把结果记进台账:平顺处理的 issue 每轮一行摘要;attempts 升到 2 或将进升级报告的争议 issue,在 history 里补记双方立场的**短原话引用**(从搭档 stdout 摘录)作为证据——只有争议才值得留原话,不做全程逐字记录。

## 子代理兜底

没有外部 CLI 时,用宿主的子代理机制(如 Claude Code 的 Agent 工具)扮演搭档:

- **同步调用并等待返回**,不要依赖子代理之间异步互发消息——实测中回传经常失败或错投,而文件 + 同步返回是可靠的。
- 简报照发(子代理同样需要知道协议),提示词模板通用;可以明确允许它跑测试,但同样禁止改文件。
- 每轮 review 用**全新的子代理**,不要复用带着旧上下文的会话——子代理和你同源,能保留的独立性只剩"没看过你的实现过程",这一点必须守住(这与外部 CLI 相反:外部 CLI 是异构模型,保持会话不损害独立性;同源子代理保持会话则会被你的叙事逐轮同化)。
- 向用户说明本次搭档是同源子代理,交叉视角弱于异构模型,重要任务可建议安装一个外部 CLI。
